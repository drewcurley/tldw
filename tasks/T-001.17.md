# T-001.17 — Write `contracts.md`

## Description
Backend (lead), with Data Engineer and Architect as co-authors, produces `/docs/contracts.md` — **the single most important doc for safe autonomous commits.** It is the exhaustive, code-grounded inventory of every contract a future change could break. Where `architecture.md` explains the shape of the system and `api.md`/`data-model.md` explain *how to extend* routes and schema, `contracts.md` is the flat index an agent scans to answer one question before touching anything: *"does my change touch something that already exists, and what depends on it?"*

This doc exists specifically to satisfy the bar in `AGENTS.md` § 6.0(3): **exhaustive, not sampled.** "etc." and "for example" are BLOCK-worthy here. If the list is long, it is still complete.

## Acceptance criteria

The inventory must enumerate **every** instance (not a representative sample) of each category that exists in the codebase, each grounded in a cited source path. Categories that don't apply to this stack are marked "N/A — <reason>", not silently omitted.

- [x] `/docs/contracts.md` exists.
- [x] **Routes / endpoints** — every HTTP route, GraphQL field/resolver, gRPC method, or equivalent: method, path, auth requirement, and a pointer to its handler. Cross-referenced with `api.md`.
- [x] **Request / response contracts** — every externally-observable request and response shape (or a pointer to the exact machine-readable schema, e.g. OpenAPI, with regeneration instructions). — **met differently:** there is no machine-readable schema, so the inventory lists every request and response key itself (`docs/contracts.md` § "Category index (T-001.17)") (plan rev 4 rule 7).
- [x] **Event / message schemas** — every published or consumed event, queue message, or webhook payload, with producer and consumer named. — **met differently:** the NDJSON stream events and the extension's port and tab messages are the event schema; webhooks are N/A (`docs/contracts.md` § "Category index (T-001.17)") (plan rev 4 rule 7).
- [x] **Public interfaces / signatures** — exported functions, modules, or library entry points other code (internal or external) depends on, where a signature change would break callers.
- [x] **Data contracts** — every table/collection and its consumers (may point to `data-model.md` for column detail, but the consumer/blast-radius mapping lives or is summarized here). — **met differently:** file-backed stores, `chrome.storage.local` keys and mirrored lists; tables are N/A (`docs/contracts.md` § "Data stores"; `docs/data-model.md`) (plan rev 4 rule 7).
- [x] **Third-party integrations** — every outbound dependency (payment, auth, email, storage, analytics, etc.): what it's used for, where it's called, and the failure/timeout expectation.
- [x] **Environment variables / config keys** — every env var or config key the system reads, what it controls, required-vs-optional, and the default.
- [x] **Feature flags** — every flag, its default, and what it gates. — **met as N/A:** no feature-flag system; the env vars and config keys that act like flags are named (`docs/contracts.md` § "Feature flags") (plan rev 4 rule 7).
- [x] **Scheduled jobs / cron / queues** — every background job: schedule, what it does, idempotency expectation. — **met differently:** cron, queues and recurring timers are N/A; every background thread, `Timer` start and sweep is listed (`docs/contracts.md` § "Scheduled jobs and background work") (plan rev 4 rule 7).
- [x] **Cross-cutting invariants** — the things that must stay true system-wide (e.g. "every write to X emits event Y", "all money is stored in minor units", "tenant isolation is enforced at the query layer"). For each: what breaks if it's violated.
- [x] For **each** entry: the **invariant** (what must stay true) and the **blast radius** (who/what depends on it) are stated, per § 6.0(4).
- [x] **Verification recorded** — the doc states how the inventory was derived and checked against the code (e.g. "enumerated routes via the router registry + OpenAPI spec; cross-checked against integration tests"), per § 6.0(5). Reviewers independently re-check against the source.
- [x] **No invented facts** — anything unconfirmed is `UNKNOWN — needs human confirmation` with a follow-up task, never a plausible guess.
- [x] If the repo is greenfield (little/no code), the doc is marked **forward-looking** and lists the planned contracts as such — not as if they already exist. — **met as N/A:** tldw is existing code, and the doc describes only what exists (`docs/README.md` § "The Grounding & Completeness Protocol (summary)").
- [x] Includes an "update-this-doc-when" footer: any change to a route, schema, event, public signature, integration, env var, or flag updates this file in the same pull request (`AGENTS.md` § 7, § 8).
- [x] No unreplaced template placeholders.
- [x] `tests/test_docs_contracts.py` is committed and runs in CI. It checks every inventory category against the code (forward and reverse), with exclusions that need reasons, a count floor per extractor and one negative test, plus the deterministic leak check. `MIN_TESTS` in `scripts/ci-tldw-tests.sh` is raised to the new total, with its fixtures.
- [x] All 9 agents have signed off.

## Risks / dependencies
- This is the highest-effort Tier 1 doc on an existing codebase. Budget for it. The cost is the point — it is what makes every later commit safe.
- Depends on `architecture.md` (T-001.2) for the system map and is the backbone for `api.md` (T-001.5) and `data-model.md` (T-001.4); draft in close coordination.
- On a large codebase, prefer pointing to reproducible machine-readable sources (OpenAPI, schema dumps) over hand-copying — but the pointer must be exact and the generation reproducible. A hand-wavy summary fails review.

## Notes
This subtask was added so the contract inventory lands in **Tier 1**, before any feature work — an agent committing the moment Tier 1 completes must already know every route and schema it could break.
