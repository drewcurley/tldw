# T-020 — Bleep, mute or moo listed words, timed to the word

> The description just below is the original request, kept as history. The scope rewrite after it is the current scope.

## Description
**The owner's request (2026-11-12, hackathon dry run):** a caption-based profanity mute. While a YouTube video plays, the extension silences the audio for each caption cue whose text contains a word from a list, and restores it afterwards.

tldw already reads the video's captions from YouTube's transcript panel (`extension/content.js:517`, `collectPageTranscript`). Each cue has a start time, `start_ms`, but no end. tldw also already drives the player with a `timeupdate` listener for "Play key moments" (`content.js:1549-1587`). This feature reuses both. It is extension-only: no server, model or cache change.

**The known limit, by design:** YouTube captions are timed per cue (a phrase of about 2–5 s), not per word. So a match mutes the whole cue, from its start to the next cue's start.

## Scope rewrite (owner, 2026-11-12): this supersedes the criteria and plans below
The owner: "let's rewrite T-020 to include this. re-run the whole lenses and process if you need to. it's the better feature."

"This" is the owner's **hybrid design**:
- **The captions find which lines hold listed words**, including YouTube's `[ __ ]` censor marker.
- **Whisper then times just those words** in short audio windows around each hit.
- **Caption-line timing is the fallback.**

Together with the owner's earlier change request, the sound is **a bleep by default, or mute, or a moo**. The criteria below replace the original ones. Plan rev 5 (to be drafted) replaces rev 1–4 and their addenda, which stay below as history. **The whole review re-runs:** three rounds, the 7 lenses, the Review Coordinator, then **the owner's approval (step 4b)**.

## Acceptance criteria
- [x] **Finding hits.** When the user turns the feature on in the panel, the caption lines that contain a listed word are found. Matching is whole-word and case-insensitive, and YouTube's `[ __ ]` marker counts as a hit. Each hit starts as a **caption-line range**.
- [x] **Word timing (Whisper, in windows).** If Whisper is available (installed, its model on disk, ffmpeg on the server, and the Whisper setting isn't `off`), the server transcribes **only a short window around each hit** with word timestamps, and locates the listed word. For a `[ __ ]` hit, it finds the word Whisper hears that is on the list, or one Whisper writes masked or as the marker itself. The range is narrowed to that word, plus stated padding. The windows, the padding and the precision are stated in the plan.
- [x] **Graceful fallback.** If Whisper isn't installed, a window fails, alignment hasn't finished by the time playback reaches the hit, Whisper finds fewer listed words than the caption line holds, or alignment is unavailable for any reason (off, busy, rate-limited, older server, unreachable), that hit uses its caption-line range. Refined ranges replace coarse ones as they arrive, and nothing waits on Whisper to start.

Bleep and moo are generated in the page, with no sound file, unless the plan justifies one with a checked license. ## Plan (rev 5 — hybrid caption + Whisper bleeper; supersedes rev 1–4 and addenda)

**Status:** draft, not reviewed. The three rounds, the 7 lenses, the Review Coordinator and step 4b all re-run on this text. Rev 1–4 below stay as history; **every finding from them that still applies is restated here**, so a reviewer never has to merge the addenda in their head. **Scope note (carried from rev 2, CEO/PM lenses):** hackathon scope on a throwaway fork; no precedent for `main`. Unlike rev 2, this **does** change the server (one new route, one new cache store, one Whisper helper). The extension half stays as rev 2–4 designed it, plus sound and refinement.

### 0. The design in five lines
1. On toggle-on, the panel reads the captions (`collectPageTranscript`, `extension/content.js:517`) and builds **caption-line ranges** for every cue that matches the list or holds `[ __ ]`. These are active at once: nothing waits on Whisper (AC1, AC3).
2. In parallel, the extension sends the server **only the time windows** around those cues, never the word list (§ 4.2).
3. The server fetches the video's audio **once**, cuts the windows locally with `ffmpeg`, and runs faster-whisper with `word_timestamps=True` on each, under the single transcription permit. It streams **every word Whisper heard in each window, with its times**, and caches each window (AC2, AC9).
4. The extension matches those words against the same pattern it used on the captions, and **replaces** a hit's caption-line range with word ranges as each window arrives, never mid-range (AC3).
5. Each range silences the video (`video.muted`) and, in bleep or moo mode, plays a sound generated with Web Audio (AC4).

### 1. Extension pure logic (`extension/content.js`, fenced by marker comments so `tests/js/` can extract it, as `tests/js/page_transcript_checks.js` does with `grab`)
All times are **media milliseconds**. `currentTime × 1000` is converted once, at the edge.

- **`resolveMuteList(stored)`** (rev 4 B3): an absent key (`undefined`) gives the default from `TLDW_MUTE_DEFAULTS`; `""` gives off; otherwise split on commas and newlines. If `TLDW_MUTE_DEFAULTS` is missing, the result is an empty list, which is off (rev 3 Backend).
- **`muteWordsPattern(list)`** (rev 2, unchanged): trim, lowercase, dedupe; cap at 200 entries of 64 characters; escape each as a literal in one alternation; Unicode boundaries `(?<![\p{L}\p{N}])(…)(?![\p{L}\p{N}])` with the `u` and `i` flags, so accented words and entries like `a$$` work. The marker `\[\s*_+\s*\]` is added **only when the list is non-empty** (rev 2 Analyst B2). An empty list returns `null` and is gated before any read.
- **`muteRanges(cues, pattern, durationMs)`** (rev 2 Data B1–B3, unchanged rules), now returning **hits** rather than bare ranges:
  - Sort; drop rows with no text or a non-finite `start_ms`, as `parse_panel_rows` does.
  - Each matched cue becomes a hit `{id, cueStart, cueEnd, kind: "word" | "marker", line: [s, e], words: null}`. The line range is `cueStart − 200` to `end`. `end` is `nextStrictlyLaterStart + 1000`, because `start_ms` comes from the panel's `m:ss` clock (`clockToMs`, `content.js:406-415`) and is rounded down by up to 999 ms. Rows that share a start second use the first *strictly later* start.
  - Every line range is capped at `cueStart + 8000`. The last cue ends at a finite `durationMs`, else at the cap; nothing ever yields `NaN`.
  - The hits' line ranges are merged into the active list as in rev 2 (overlapping or touching ranges merge), and the function returns hits, active ranges, the count N and the total ms.
- **`alignWindows(hits, nowMs, durationMs)`** (new): one window per hit, `[max(0, cueStart − 1000), min(duration, cueEnd + 500)]`, capped at **12 000 ms** (`[cueStart − 1000, cueStart + 11 000]` when longer). Two windows are joined only if the joined window is still ≤ 12 s; otherwise they may overlap, and duplicates are removed later by range merging. Windows are **ordered for progressive refinement**: those ending at or after `nowMs` first, ascending, then the earlier ones. At most **200** are sent; any further hits stay line-timed. Every input is a whole second plus a fixed offset, so the same caption track gives the same windows, which keeps the server's cache keys stable.
- **`refineHit(hit, windowWords, pattern)`** (new). `windowWords` is the server's `[{s, e, w}]` for that window (§ 3.3):
  - Normalise each `w`: NFC, trim, and strip leading and trailing characters that are not `\p{L}`, `\p{N}`, `$`, `@`, `*` or `_`.
  - **A word hit:** every Whisper word the pattern matches.
  - **A marker hit (`[ __ ]`):** the same, plus any word that looks masked (`^\p{L}?\*+\p{L}*$`) or is Whisper writing the marker itself (`^\[?_+\]?$`).
  - Each match becomes a range from `s − 150` to `e + 100`, at least 300 ms long, kept only if it lies inside the window and is under 2 s (a sanity bound against a bad timestamp).
  - No match leaves `words: []`, and the hit keeps its line range. That is the fallback, reported as "by caption line".
- **`applyRefinement(state, hitId, wordRanges, nowMs)`** (new): if the playhead is **inside** that hit's active line range, the refinement is queued and applied when the playhead leaves it, so a range never shrinks under the user mid-word. Otherwise it is applied at once. Then the active list is re-sorted and merged again. Each range carries `timed: "word" | "line"`. The counts: N hits, K hits with at least one word range.
- **`muteStep(state, input)`** gives `{action: "enter" | "exit" | "none" | "teardown", sound: "start" | "stop" | "none", state}`. Its input is `{nowMs, videoMuted, videoVolume, videoId, adShowing, paused, userSignal}`. Carried forward:
  - **Ownership (rev 2 Data; rev 3 Frontend B1).** The feature unmutes only a mute it set itself. `volumechange` releases ownership **only** when `video.muted` differs from the value the feature last set, so a volume-slider move, which fires `volumechange` without changing `muted`, doesn't. A `.ytp-mute-button` click, or an `m` keydown outside an editable target (`input`, `textarea`, `contenteditable`, YouTube's search box), releases ownership and leaves `muted` as it is. That covers a user muting while the feature already has the video muted, which fires no event. If the video was already muted when a range began, the feature takes no ownership **and plays no sound**.
  - **The user's sound wins (new, AC7).** A release of ownership during a range also stops the bleep or moo: a user who mutes wants silence, and a user who unmutes wants the video. A `videoVolume` of 0 means no sound is started. A volume change during a sound re-scales its gain (§ 2) and changes no ownership.
  - **Ads (rev 3 Frontend B2):** while `adShowing` (`#movie_player` has `.ad-showing`), the feature unmutes if it set the mute, stops any sound, and returns `none` until the ad ends.
  - **Pause and seek:** a pause stops the sound and keeps the mute. A seek re-evaluates from scratch (out of range: exit; into a range: enter).
  - **Teardown:** a change in the page's video id returns `teardown`.
- **`nextBoundaryDelay(state, nowMs, playbackRate)`** (new): the wall-clock ms to the next range edge, or `null` when more than 1 s away. Rev 2 relied on `timeupdate` (about every 250 ms), which is too coarse for a 300 ms word: a word could be skipped entirely. The wiring therefore also sets a `setTimeout` for that delay, and re-evaluates on `timeupdate`, `seeked`, `play`, `pause` and `ratechange`. `timeupdate` stays the backstop. Chrome doesn't throttle timers in an audible tab; whether a hidden tab **in mute mode** gets throttled after five minutes is `UNKNOWN — needs review` (Frontend), and the backstop bounds the damage to about 250 ms.

### 2. Sound modes
- **Storage key `muteSound`** (new, `chrome.storage.local`): `"bleep"` (default) | `"mute"` | `"moo"`. Absent or unknown means `bleep`. `content.js` reads it with `storage.local.get("muteSound")` at toggle-on, beside `get("muteWords")` (rev 2 Data: read only these keys, and add no second `onChanged` listener). Edits take effect the next time the feature is turned on. `options.js` reads both with `get(["muteWords", "muteSound"])`, separate from `get(DEFAULTS)` (rev 3). Its Save write grows **from 7 keys to 9** (`options.js:137`). Neither key goes in `getSettings`/`DEFAULTS` in `background.js`, nor into any request body (rev 3 Backend; the three-places rule holds because `background.js` reads neither).
- **Every mode silences the video** with `video.muted = true` under the ownership rules. Routing the video through Web Audio (`createMediaElementSource`) is rejected: it captures the element for the life of the page, and a cross-origin media source without CORS outputs silence. Whether googlevideo sends CORS headers is `UNKNOWN`, and it isn't worth finding out.
- **Bleep:** an `OscillatorNode`, `sine`, **1000 Hz**, through a `GainNode`. Peak gain is **0.15 × `video.volume`**, so the bleep is never louder than the user's own volume setting. Attack is a 5 ms linear ramp, release a 10 ms ramp at the range end, to avoid clicks. It plays for the **whole range**: that is what a broadcast bleep does, and line ranges are capped at 8 s. A word range is typically 0.4–0.8 s. (The UX review may want it shorter on line ranges; see open questions.)
- **Moo**, synthesised so no asset and no license is involved (the Architect's licensing item is closed by construction):
  - **Source:** a `sawtooth` oscillator. Its pitch goes 105 Hz → 135 Hz over the first 25 % (exponential ramp), then down to 95 Hz at the end.
  - **Vibrato:** a 5 Hz `sine` LFO, ±3 Hz, into `osc.frequency`.
  - **Formant** ("mm-OO-oo"): a `BiquadFilterNode` `lowpass`, Q 6. Its cutoff goes 350 Hz → 900 Hz at 35 % → 400 Hz at the end.
  - **Envelope:** attack 80 ms (or 20 % of the moo if that is shorter), release over the last 200 ms (or 30 %).
  - **Level:** peak 0.25 × `video.volume`. Loudness against the bleep is `UNKNOWN — needs review`; the real-browser check tunes it.
  - **Rule for long ranges: one moo per range**, lasting `clamp(rangeMs, 250, 1500)` ms. Past 1.5 s, the video stays muted, silently, until the range ends. **Why not repeat:** the only ranges over 1.5 s are caption-line fallbacks, up to 8 s, so repeating would give up to five moos for one word. That draws more attention than the word did, and a fallback range is exactly where we are least sure a word is there. A moo is longer than most word ranges, so it may run up to about 250 ms past the unmute. That is additive sound over the video, and it hides nothing.
- **Pure plans, thin player:** `soundPlan(mode, rangeMs, volume)` returns a list of automation events (`{node, param, kind, value, at}`) with no Web Audio in it. `playPlan(ctx, plan)` applies it, and returns a handle whose `stop()` ramps down in 10 ms and disconnects. The plans are tested exactly; the player is tested against a stub context.
- **Autoplay in a content script.** The `AudioContext` is created **lazily, inside the toggle's click handler**, which is a user gesture in the page's document (the panel lives in the page's DOM, in a shadow root). `resume()` is called there too. The toolbar click is not a page gesture, so nothing is created at injection. Mute mode never creates a context.
  - If the context isn't `running` when a range starts, or `resume()` rejects, that range is **muted only** and the status says so once (the message is in § 5).
  - A re-opened panel reuses the live context.
  - Teardown calls `ctx.close()`.
  - No new manifest permission is needed. Firefox's autoplay policy is assumed to behave the same way: `UNKNOWN — needs review`, and the Firefox browser check covers it.

### 3. The alignment path, end to end
**3.1 Decision: a new route, `POST /align/stream` (NDJSON).** It is not an extension of `/segments/stream` or `/summarize/stream`: those are claude-pool routes with `_validate`, a `url` and model semantics (`server.py:1017-1049`). This route takes no claude slot and has a different body.

- **Where it is defined:** the `do_POST` early chain, beside `/ask/stream`, as `self._guarded(self._run_align, slots=None)` (`server.py:1014-1016`; `_guarded` at `server.py:1102-1127`). It returns before the "not one of ours" tuple (`server.py:1017`). It uses the default `MAX_BODY_BYTES` of 16 KiB (`server.py:542`): 200 windows at about 40 bytes each fit. `_body_limit` is unchanged. `do_GET`, `do_OPTIONS` and CORS `Allow-Methods` are unchanged.
- **Request body:** `{"url": str, "whisper": "off"|"ask"|"always", "windows": [{"start_ms": int, "end_ms": int}, …]}`.
  - `url` goes through `canonical_video_id`; nothing else from the body reaches argv.
  - `whisper` goes through the existing `_whisper_policy` (`server.py:136-160`). A server-pinned or client `off` means 503, "Whisper is turned off", with no work done (open question 4).
  - `windows` is parsed by `align.parse_windows`. It must be a list of 1–200 objects; each value an `int` (not a `bool`); `0 ≤ start_ms < end_ms`; `end_ms − start_ms ≤ 12 000`; `end_ms ≤ _max_transcribe_ms()`. Anything else is a 400 naming the field. Overlapping windows are allowed.
- **Response:** `200`, `application/x-ndjson`, sent with the same headers as `_run_stream` (`server.py:1190-1197`). One JSON object per line:
  - `{"type":"progress","message":…}`, an existing type.
  - `{"type":"window","i":<index into the request>,"start_ms","end_ms","words":[{"s":ms,"e":ms,"w":str}],"cached":bool}`, a **new type**. At most 200 words per window; `w` at most 64 characters; `s` and `e` absolute media ms, clamped to the window.
  - `{"type":"result","timed":n,"cached":n,"failed":n}`.
  - `{"type":"error","status":…,"error":…}`, which ends the stream. Windows already sent stay valid.
  - Before streaming starts, plain JSON errors are possible: `400`, `401`, `413`, `415`, `411` (from `_read_body`, `server.py:1129-1150`), and `503` (Whisper missing or off; `install_hint` included when missing, as `server.py:1409` does).
- **Server flow (`_run_align`):**
  1. Validate. Then look up **every window in the cache first**, and emit hits immediately (`cached: true`). If all hit: `result`, done. **No yt-dlp call and no permit.**
  2. `whisper_transcribe.is_available()`, else 503 with `INSTALL_HINT` (`whisper_transcribe.py:55-62`). This is checked before any download, which is the same reason `transcribe_video` checks first (`whisper_transcribe.py:276`).
  3. **One alignment at a time, process-wide:** a non-blocking `_align_lock`. A second concurrent request gets an in-stream `{"type":"error","status":429,"error":"Already timing words for another video. Try again when it finishes."}`. This bounds parallel YouTube fetches, since two tabs can't each start a download.
  4. **Rate-limit cooldown:** if `_align_backoff_until` is in the future, error 429 with the rate-limit text (§ 3.2). No fetch.
  5. **Audio:** `download_audio(vid, workdir, timeout=ALIGN_DOWNLOAD_TIMEOUT, max_duration_s=_max_transcribe_ms() // 1000)`, into a `tempfile.mkdtemp(prefix=hygiene.AUDIO_TMP_PREFIX)` directory, so the existing stale-audio sweep covers a crash (`server.py:88-104`). It is **outside** the transcription permit, because it is network I/O and not CPU. Errors go through `metadata._translate`, and a rate-limited one sets the cooldown.
  6. **Permit:** acquire `_tx_permit` with the existing 0.5 s poll (`server.py:243-245`), emitting `progress` "Waiting for Whisper: a transcription is running…". **Give up after 20 s** with an in-stream 429, "Whisper is busy transcribing another video. Try again when it finishes." A whole-video transcription can hold the permit for most of an hour, and alignment is only an improvement; the line ranges already work. The permit is held for the model load and all the windows, then released in `finally`.
  7. **Model:** `whisper_transcribe._load_model(resolve_model(), local_only=True)`, a helper factored out of `transcribe()` (`whisper_transcribe.py:199-210`) that both now call. `local_only=True` passes `local_files_only=True` to `WhisperModel`, so **alignment never triggers a 75 MB–3.1 GB model download** while holding the permit. A missing model is a 503, "Whisper's model isn't downloaded yet…". Factoring it keeps `model_download_sites` at one `WhisperModel(...)` site (floor 2, `tests/test_docs_contracts.py:584-592`).
  8. **Per window,** in request order:
     - cut it with `ffmpeg -nostdin -loglevel error -ss <to_ffmpeg_ts(start)> -t <dur> -i <audio> -ac 1 -ar 16000 -f wav <workdir>/w<i>.wav`, where every argv item is a server-made number or path (`timing.to_ffmpeg_ts`);
     - transcribe with `beam_size=5, word_timestamps=True, vad_filter=False, condition_on_previous_text=False, language=None`;
     - collect `seg.words` into `[s, e, w]` with `s = window_start + round(word.start × 1000)`;
     - cache it, emit `window`, delete the wav;
     - check the deadline and the client between windows.
     
     A window that fails, or that hits the per-window deadline, is counted `failed` and skipped. It is never cached, and the others continue.
  9. **Client gone:** a write that raises `OSError` (a `BrokenPipe`) ends the loop after the current window. The windows already finished are cached, so a re-toggle resumes cheaply. Unlike `_start_transcription` (`server.py:187-300`), this is **not** a background job: if the user navigated away, there is nobody left to bleep for.
  10. `finally`: remove the workdir and release the lock and the permit.
- **Timeouts:** `ALIGN_DOWNLOAD_TIMEOUT = 300 s`; per window 30 s (`transcribe`'s `deadline` pattern, `whisper_transcribe.py:230-233`); a whole-request budget `ALIGN_BUDGET_S = 600 s`. Extension safety timer: 620 s. Pings every 20 s keep the MV3 worker alive (`background.js:81`; the pattern is `content.js:1490`).

**3.2 Decision: full audio once per request, not `--download-sections`.**
- **YouTube's rate limit counts extractions, not bytes.** Both options cost **one** yt-dlp extraction per request: sections are one invocation with N ranges. So the rate-limit cost is the same, and the cache-first rule makes it **zero** for any window seen before.
- **Full audio reuses the proven, already-hardened `download_audio`** (`whisper_transcribe.py:102-151`: `bestaudio` with no muxed fallback, `--max-filesize`, `!is_live`, `--ignore-config`, the reported-path pick, tested at `tests/test_whisper_transcribe.py:209-262`). Sections would mean a new ffmpeg-driven yt-dlp download mode, with its own failure modes on DASH audio: `UNKNOWN`, and it would need a spike.
- **Cost:** bytes and time on long videos, about 1 MB a minute, so about 20 MB for 20 minutes and about 120 MB for two hours. That is bounded by the new `max_duration_s` (the `whisper_max_minutes` ceiling, `server.py:125-133`) and the existing 300 MB cap. Open question 1 asks whether sections are worth a spike for long videos.
- **Rate-limit behaviour, per `docs/runbooks/youtube-rate-limit.md`:**
  - No `_RETRY` on this download (unchanged from `download_audio`, so no retry storm under a throttle).
  - The 429 text comes from `_translate` (`metadata.py:66-76`).
  - A **10-minute process-wide cooldown** after a 429, during which alignment does no fetch and the extension keeps line ranges.
  - **The extension never retries automatically:** one request per toggle-on.
  - Cookies (`_cookie_args`, `metadata.py:52-55`) are **not** passed, the same as the Whisper download today (`docs/data-model.md:278`). That is open question 2.
- **`download_audio` gains `max_duration_s: int | None = None`.** When set, the match filter becomes `!is_live & duration <= N`, with N a server int. When it is `None`, the argv is **byte-identical** to today's (tested).

**3.3 Word matching happens in the extension, and the list is never sent (§ 4.2).** The server returns every word in each window. The extension runs `refineHit`. For a `[ __ ]` hit, the listed word Whisper hears, or a masked one, is taken.

**3.4 Precision and padding.**
- **Word range:** `wordStart − 150 ms` to `wordEnd + 100 ms`, at least 300 ms. **Line range:** `cueStart − 200 ms` to `nextStart + 1000 ms`, at most 8 s (rev 2).
- **Expected precision:** faster-whisper's word timestamps are typically within about 100–300 ms of the true edges. That figure is **not measured here**: `UNKNOWN — needs review`. The real-browser check measures it on three test videos (a word mid-sentence, a fast talker, music behind speech) and records the result in the review artifact.
- **Trigger jitter** with the boundary timer is about 4–15 ms. Audio output latency is about 20–50 ms. Both are inside the padding.
- **Net effect:** about 0.5–0.8 s covered per word, against 3–8 s per caption line.

**3.5 Cache, a new store 9: `~/.cache/youtube-tldw/align/<video_id>-<16 hex>.json`, one file per window.**
- **The key is the sha256 of `video_id|start_ms|end_ms|whisper_model|ALIGN_FINGERPRINT`**, where `ALIGN_FINGERPRINT` is the first 12 hex digits of the sha256 of:
  - the transcribe keyword arguments, as a sorted JSON dict: `beam_size`, `word_timestamps`, `vad_filter`, `condition_on_previous_text`, `language`, `compute_type`;
  - the ffmpeg cut arguments, sample rate and channel count;
  - `MAX_WORDS_PER_WINDOW` and the word-text cap;
  - `importlib.metadata.version("faster-whisper")`, since a library upgrade changes timestamps;
  - **`ALIGN_SHAPE = 1`**, the payload shape's own version.

  That last term closes the gap `docs/data-model.md:365` records for summaries ("no fingerprint covers the `_to_payload` shape") and the "not in the key" list at `docs/data-model.md:71`. Every constant that shapes the result goes in, and a test asserts that changing any one of them changes the key.
- **The words list is deliberately not in the key.** The cached result is "what Whisper heard", which the list doesn't shape, because matching happens in the browser. Editing the list therefore needs no re-transcription. This satisfies AC9's "everything that shapes them": the list shapes the **match**, which is computed client-side and never cached. `lang` isn't in the key either, because `language=None` (auto) is fixed in the fingerprint. Open question 3.
- **Payload:** `{"saved_at", "video_id", "start_ms", "end_ms", "words": [[s, e, w], …]}`. It is **validated on read** (types, bounds, count); anything off is a miss, never an error. That fixes the "segment item shape is not validated on read" weakness for this store.
- **TTL and cap:** `TTL_SECONDS` (14 days, `txcache.py:26`); its own cap `ALIGN_MAX_ENTRIES = 5000`. `_prune` gains an optional `cap` parameter, with the default unchanged (`txcache.py:95-99`).
- **Writes:** atomic `.tmp` then `replace`, best effort, the same as `put_segments` (`txcache.py:154-164`).
- **Data class:** like the transcript cache (store 1): text derived from public video audio, which also reveals that this video was watched.
- **`tldw cache`** reports the new area and `tldw cache clean` prunes expired entries, like the other stores (`docs/data-model.md:296`). This is a small `cli.py`/`hygiene.py` change. Open question 6 asks whether it is in scope.

**3.6 Extension → background → server.**
- **The port.** `content.js` opens its **own** `api.runtime.connect({name: "tldw"})` port, `alignPort`, owned by the mute session (not the panel), so closing the panel doesn't drop it (AC8). It posts `{type: "align", url, windows}`.
- **`background.js`** gains `handleAlign(port, msg)`, dispatched in the `onConnect` chain (`background.js:70-81`):
  - it reads `getSettings()` for the server URL, the token and `whisper` (`background.js:43-51`);
  - it `fetch`es `POST /align/stream` with `Authorization: Bearer` and an `AbortController`;
  - it parses the NDJSON and forwards each event as a port message;
  - it aborts the fetch on port disconnect.
- **New port types** (content ← background): `alignWindow {i, words, cached}`, `alignProgress {message}`, `alignDone {timed, cached, failed}`, `alignError {status, error}`. `align` is new in the other direction (content → background). `ping` is reused.
- **`alignError(status, detail)`** maps the statuses, the same way `httpError`/`askError` do (`background.js:440-447`, `:571-581`): 401 token, 404 (an older server with no such route), 429 detail, 503 detail, 504, a network failure, and anything else.
- **Stale messages.** Every content-side handler checks `alignPort` is still the live one, and that the video id hasn't changed. The video id is recorded before the request, the same check `summarizeFromPage` uses (rev 3 B3). Anything else is dropped.

**3.7 The fallback and progressive-refinement rule (AC3).**
1. Line ranges go active as soon as the captions are read.
2. Refinements apply per hit as they arrive, deferred while that hit is the active range (§ 1).
3. Any hit not refined — not reached yet, failed, or no word found — keeps its line range for as long as the feature is on.
4. Any failure of the whole request leaves **all** hits on line ranges, with a status naming the reason and a next step.
5. Nothing ever waits on alignment.

### 4. Security
- **4.1 Server.**
  - Loopback-only bind (`server.py:1933-1940`); the bearer token compared with `hmac.compare_digest` via `_guarded` (`server.py:955-960`, `:1102`); CORS fails closed (`server.py:917-924`); the 16 KiB body cap; JSON only, no chunked bodies (`server.py:1129-1150`).
  - **Argv:** the video id is canonical; windows are validated ints rendered by `to_ffmpeg_ts`; paths are made by the server inside its own `mkdtemp`. No shell (`proc.run`, `proc.py:66-103`). Window text never reaches argv. `--ignore-config` stays.
  - **Resources:** at most 200 windows × 12 s = 40 minutes of audio, which at the measured 5.5× (`whisper_transcribe.py:44-50`) is at most about 7.3 minutes of CPU, under `ALIGN_BUDGET_S` (600 s). One alignment at a time; the shared permit; no model download; the duration ceiling; the 300 MB cap.
  - **Logging:** the default access log only (method, path, status). Words and windows are never printed.
- **4.2 The word list stays in the browser.** Matching client-side costs bytes: about 30 words per window come back instead of 1. In exchange:
  - the list never crosses a process boundary, and never lands in server logs or caches (rev 2's privacy line holds: "the word list never leaves the browser");
  - list edits need no re-transcription;
  - the server cache key needs no list term.

  **What does leave:** the window times, which only show *where* the captions contain a listed word, and only to the user's own loopback server. That is stated in `architecture.md` § 8.
- **4.3 The extension.**
  - Server words are only ever compared with a regex. They are **never** inserted into the DOM.
  - The pill and statuses are built with `createElement`/`textContent`, never `innerHTML` (rev 2).
  - `mute_words.js` uses `globalThis.TLDW_MUTE_DEFAULTS ??= [...]` with **no top-level `const`/`let`**, because `executeScript` re-runs it on every toolbar click (`background.js:61`). A top-level `const` would throw on the second click (rev 2 Architect B1; `content.js:6-7` guards itself the same way).
  - No new manifest permission.
- **4.4 Profanity hygiene (rev 4 DevOps):** the default words live **only** in `extension/mute_words.js`: never in docs, task files, review artifacts, the PR body or commit messages. Test fixtures use made-up words.

### The 7 lenses on rev 5–5.3 (the hybrid design)
1. **CEO: support.** This is a hackathon demo on a fork that gets thrown away, and the story is "the playbook took a feature from request to reviewed plan". The reputational risk is the default word list. It is mitigated by a hand-written mild list with no slurs, kept only in `mute_words.js`, which the owner reads at step 4b (AC6). It sets no precedent for `main`.
2. **Purchasing: support.**
   - No new dependency. faster-whisper is already the optional `whisper` extra, and ffmpeg is already a documented prerequisite.
   - No sound asset and no licence, since both sounds are synthesised.
   - No Claude usage, so no plan cost.
   - The cookie database is not read (Q2).
   - The YouTube rate-limit exposure is one extraction per uncached toggle, with a cooldown.
3. **Product/PM: support with a condition.** This is the largest T-020 revision: one route, one cache store, and the extension's sound and refinement. But every piece is bounded, and caption-line covering works on its own, so the build can land in layers (pure logic, then wiring, then the server) with tests at each. **The condition:** the build is sized at roughly a day of agent work, longer than rev 4's. If it slips, the owner's stated fallback is caption-line covering only. That fallback is a named, coherent cut, not a half-feature.
4. **Adopter: support.**
   - Bleep is the familiar broadcast convention, and it is capped at 1.5 s.
   - Moo is the demo's delight moment.
   - Word timing turns 3–8 s of covered speech into about 0.5–0.8 s, which is what makes it watchable.
   - The friction: it is per tab, per video, and turned on in the panel. That is honest, and stated in `ux.md`.
5. **Builder: support.**
   - Pure functions are fenced and tested, and the wiring takes its dependencies as parameters.
   - The server path reuses `download_audio`, `_guarded`, the permit and the cache patterns, rather than forking them.
   - Every error carries `reason`, and logs carry the reason, never words.
   - The cost is a large test register, which is what makes it something you could be on call for.
6. **Investor: neutral.** There is no market claim. The value is demonstrating disciplined agentic delivery on a playful feature.
7. **Marketing/Sales: support.** The 60-second hook: "Click once, and every listed word gets a bleep, or a moo, timed to the word." It demos well: toggle, see the hit count, hear a word-timed bleep, switch to moo. The predictable objection, "does it catch everything?", is answered honestly: only words in the captions, and not a parental control (`ux.md`).

**Conflicts between lenses:**
- **PM vs. Adopter, on build size against the word-timing payoff.** Resolved by the layered build and the named fallback cut. The owner explicitly chose the hybrid ("it's the better feature").
- **Investor (neutral) vs. Marketing (support).** No conflict: the fork carries no market claim.
- No lens opposes.

## Original acceptance criteria (superseded, kept for history)
- ~ **Given** a video whose transcript panel can be read, **when** the user turns on "Mute listed words" in the panel, **then** the video is muted for every cue containing a listed word and unmuted when that cue ends. A word matches as a whole word, case-insensitive, so "classic" doesn't match "class". **YouTube's own censor marker `[ __ ]`**, which auto-generated captions use in place of profanity, also counts as a match.
- ~ **A mute span** runs from the cue's start to the next cue's start. The last cue ends at the video's end, or at a cap the plan states. Both the cap and any lead-in padding are stated in the plan.
- ~ **The panel says what is happening:** how many spots will be muted, an `aria-live` announcement when the mode turns on or off, and a visible indicator while a mute is active.
- ~ **The word list** has a built-in default and can be edited in Options, as a new `chrome.storage.local` key. An empty list turns the feature off.

While muting is on, a small pill on the player shows it, and turning it off there or in the panel works. **Turning it off, or moving to another video,** restores the audio state the feature changed and removes every listener it added.

- ~ **Automated tests** cover matching, span building, the user-mute rule, and teardown, through the node `vm` harness in `tests/js/`. `MIN_TESTS` is raised.

## Plan rev 5.5: the moo rework (owner, 2026-11-13; overrides the moo bullets in rev 5 § 2)

**Why:** in the owner's real-browser check (AC4), the moo "sounds more like a fart". The rev 5 moo is a 95–135 Hz sawtooth through one resonant lowpass, and the lowpass never opens past 900 Hz. That leaves mostly low, buzzy energy with no vowel in it. At the 250 ms floor, which is most word-timed ranges, nothing in it says "cow".

**What changes (`soundPlan("moo", …)` and `playPlan` only):**
- **Pitch, higher and voiced:** a `sawtooth` going 120 Hz → 155 Hz at 30 % (exponential), then down to 110 Hz at the end. Vibrato is a 4.5 Hz `sine` LFO at ±2 Hz.
- **No rumble:** a `highpass` at 90 Hz (Q 0.7) right after the source. Sub-100 Hz energy is the main thing that reads as flatulence.
- **A vowel ("mm-OO-oo"), made from two formants in series:**
  - F1 is a `peaking` filter (Q 3, +9 dB) gliding 300 → 650 Hz at 35 %, then to 450 Hz at the end.
  - F2 is a `peaking` filter fixed at 1100 Hz (Q 4, +5 dB).
- **A mouth that opens and closes:** a final `lowpass` (Q 0.7) gliding 450 Hz → 2400 Hz at 30 %, then to 1000 Hz at the end. This is the "m" onset and the "oo" close.
- **Envelope:** attack is `min(100 ms, 25 %)` and release `min(250 ms, 35 %)`.
- **The chain stays linear** (osc → hp → f1 → f2 → lp → env → vol), so `soundPlan` keeps its data shape. Filter nodes gain an optional `gain` (dB), which `playPlan` sets when present. Filter events name their node by id, as the osc's do.

**What does not change:** the level stays at 0.25 × `video.volume` on the output gain. The length rule stays at one moo per range, `clamp(rangeMs, 250, 1500)`, with the ≤ 250 ms ring-out. Bleep and mute are untouched, as are ownership, ranges and teardown. So no `/docs` text changes: `contracts.md`, `ux.md`, `domain.md` and `glossary.md` describe only the level, the cap and the ring-out, all kept.

**Loudness guard:** ~~the new peak sample must be no higher than the old one~~. **Replaced by the plan-review amendment below:** the new moo is at most 1 dB louder than the rev 5 moo **by RMS** (a CI test), plus a real-browser render of peak and RMS for the record. ## Plan rev 5.6: settings apply live (owner, 2026-11-13; overrides "read at toggle-on only")

**Owner:** "if i have a video loaded and processed, and then switch from a moo to a bleep, it still moos. settings should be hot reloaded whenever possible."

**Scope (Analyst to confirm):** every other setting is already live:
- the worker calls `getSettings()` per request (`background.js`);
- `closeAction` has its `onChanged` branch (`content.js:50-56`);
- `voice` and the sponsor keys are read when used (`contracts.md` § storage).

Only `muteSound` and `muteWords`, read once at toggle-on, are not. This rev makes those two apply to a running "Cover listed words" session. Nothing else changes.

**1. One listener, not two.** Rev 2 Data said to add no second `onChanged` listener, and that holds. The existing listener at `content.js:50` gains one branch: when `area === "local"` and `changes.muteSound || changes.muteWords`, it calls `onMuteSettings(changes)`. That is a `let` set to `null` at the top and assigned right after `muteCover` is created, so a change that arrives before then is a no-op, not a TDZ error. It passes only `newValue` for those two keys; nothing else from `changes` is read. (The token-in-`changes` exposure, `architecture.md` risk 13 / T-004, is unchanged: the listener already receives it.)

**2. `muteCover.settingsChanged({ sound?, words? })`.** Each field is `{ newValue }` when that key changed. A removed key (`newValue` undefined) resolves exactly as at toggle-on: `bleep`, or the shipped default list. With no session it does nothing, since the next toggle-on reads storage anyway.

**3. A sound change** (resolved through `MUTE_SOUNDS`; the same mode is a no-op):
- **While loading** (`!sess.active`): set `sess.mode`. Going to `mute` closes the context; leaving `mute` with no context makes one (see below). `load` then uses `sess.mode`. To close the race where `getSound` resolves after a change, `load` only takes the stored sound if no change arrived (`sess.modeSetLive`).
- **While on:**
  - Stop any playing sound (`stopSound`, `soundOn = false`), then set `sess.mode` and `sess.st.mode`.
  - The current range, if any, stays muted (ownership unchanged); the new sound starts from the next range entered. A range already in progress gets no sound.
  - **Context:** to `mute`, `closeCtx`. From `mute` with no context, create one with `new AudioCtx()` plus `resume()` outside a gesture. Chrome lets it run if the page has had a user activation (the user clicked play, or the toggle). If it doesn't run, the existing `startSound` path mutes only and says `soundBlocked` once, with no new code path.
  - **Pill:** `buildMutePill` gains `setMode(mode)`, which updates the emoji, the label base and the Stop button's `aria-label`; `setNow` keeps working.
  - **Status (new, announced):** `Sound changed: {verb} {n} from the next one.` The trailing status (on/progress/done) is not re-worded; this line replaces it until the next status.

**4. A word-list change while on** (`sess.cues`, the cues `load` read, is now kept on the session, in memory only and never sent):
- **New list empty:** end the session as Stop does, releasing an owned mute, removing listeners, ending the port and closing the context. Then say the existing `emptyList` text instead of "off".
- **No caption line matches:** end it the same way and say the existing `noMatches` text.
- **Otherwise, a rebuild in place:**
  - stop the sound, give up an owned mute (`video.muted = false` only if we set it), and end the alignment port;
  - build `muteRanges` from `sess.cues` with the new pattern, as a fresh `sess.st` (videoId and mode kept);

## Plan (2026-11-12, rev 2: after the Round 1 review and the 7 lenses)

**Scope note (the lenses' CEO and PM):** this is a **hackathon-scope feature on a fork that gets thrown away**, a demo of the playbook. It is not a product direction for tldw, and it sets no precedent for `main`. It is extension-only: no server, model, cache or manifest-permission change.

**Honest limits, stated in the UI and `ux.md`:**
- It mutes whole caption lines, not single words.
- It works only after the user clicks TL;DW on that video (injection is by click, `activeTab`).
- It isn't supported on live streams.

1. **Pure logic.** Milliseconds throughout; `currentTime × 1000` is converted once.
   - **`muteWordsPattern(listString)`** returns a RegExp, or `null` when the list is empty.
     - It trims, lowercases and dedupes the list, and caps it at 200 entries of 64 characters each.
     - Each word is escaped as a literal inside one alternation.
     - Boundaries are Unicode lookarounds with the `u` flag: `(?<![\p{L}\p{N}])(…)(?![\p{L}\p{N}])`, so accented words and entries like `a$$` work.
     - YouTube's censor marker is matched loosely as `\[\s*_+\s*\]`, but **only when the list is non-empty**. An empty list is "off", gated before the pattern is built (Analyst B2).
   - **`muteRanges(cues, pattern, durationMs)`**, named "mute ranges", not "spans", so it doesn't collide with `Span`/`spans.py` (Data):
     - Cues are sorted, and bad rows (no text, a non-finite start) are dropped, as `parse_panel_rows` does.
     - Each matched cue gives a range from `start − 200 ms` to `end`. Here `end = nextStrictlyLaterStart + 1000 ms`, because `start_ms` comes from the panel's `m:ss` clock and is rounded down by up to 999 ms (`content.js:406`; Data B1). Rows that share a start second take the first *strictly later* start (Data B2).
     - **Every range is capped** at `start + 8000 ms`, so a gap after a matched cue can't mute tens of seconds (the lenses' PM, Data). The last cue also ends at `durationMs` when known. A missing or non-finite duration never yields `NaN`: the cap applies (Data B3).
     - Ranges that overlap or touch are merged.
     - It returns ranges, a count, and the total muted ms.
   - **`muteStep(state, nowMs, videoMuted, videoId)`** returns `{action: "mute" | "unmute" | "none" | "teardown", state}`.
     - **Ownership:** the feature unmutes only a mute it set itself. A `volumechange` that the feature didn't cause, during a range, releases ownership, so a user's own mute or unmute is never overridden (Data). If the video was already muted when a range began, the feature doesn't take ownership.
     - **Teardown:** a change in the page's video id returns `teardown`.
     - **Timing tolerance (Analyst B3):** `timeupdate` fires about every 250 ms. With the 200 ms lead-in, a range is entered at most about 250 ms after its start. Tests assert decisions at sampled times, not wall-clock behaviour.
2. **One source for the default list** (the lenses' Builder, Purchasing):
   - A new file, `extension/mute_words.js`, defines the default once, as `globalThis.TLDW_MUTE_DEFAULTS ??= [...]`, with **no top-level `const`/`let`**. `executeScript` re-runs it on every toolbar click (`background.js:61`), and a top-level `const` would throw "already declared" on the second click. That would break the panel, which `content.js` avoids with its `window.__tldwInit` guard (`content.js:5-7`; Architect, rev 2). A test runs the file twice in one `vm` context and expects no error.
   - It is loaded by `options.html` (a `<script>` before `options.js`) and injected **with** `content.js` by `background.js`'s `executeScript` files list.
   - **That is a contract change:** the injected files and `build-firefox.sh`'s copy list (`extension/build-firefox.sh:10-12`) both gain the file. Both are recorded in `contracts.md`. A test checks that `build-firefox.sh` copies every file the manifests and `executeScript` reference. That copy list is "unguarded" today (T-010), so this guard is added for this file at minimum.
   - **The default content (Analyst B1, the lenses' CEO and Purchasing):** a short list of mild, common profanity, **hand-written, with no slurs**, and nothing copied from a published or licensed list. The owner persona owns it, and can edit it in Options.
3. **Storage key `muteWords`** (a string). **Never set** (`undefined`) means the default applies. `""` means off (Data).
   - `content.js` reads **only** this key, with `storage.local.get("muteWords")`; an absent key means "never set" (Data, rev 2), and adds no second `onChanged` listener (Architect). Edits made while muting is on take effect the next time it's turned on (Analyst).

## Plan (2026-11-12, rev 1)

**The shape:** extension-only, in `extension/content.js`, plus a setting in Options. No server, model, cache or manifest-permission change.

1. **Pure logic, so it can be tested:**
   - `muteWordsPattern(words)` builds one case-insensitive, whole-word regex from the list, escaping regex characters. It also always matches YouTube's censor marker `[ __ ]`.
   - `muteSpans(cues, pattern, durationMs)` turns cues (`{start_ms, text}`, sorted) into merged spans `[startSec, endSec]`. Each span runs from 200 ms before the cue's start to the next cue's start. The last cue ends at `min(durationMs, start + 5000)`. Spans that overlap or touch are merged.
   - `muteStep(state, nowSec, videoMuted)` returns the next action: `"mute" | "unmute" | "none"`. It encodes the user-mute rule: if the video was already muted when a span began, the feature never unmutes it. If the user unmutes during a span, it isn't muted again until the next span.
2. **Wiring:**
   - **The panel control:** a "Mute listed words" toggle button (`aria-pressed`) in the result view, next to Listen and Key moments.
   - **Getting cues:** turning it on reuses the cues the summarize flow already read for this video, if it has them. Otherwise it calls `collectPageTranscript()` (`content.js:517`).
   - **Building and attaching:** it builds the spans and attaches a `timeupdate` listener to `video.html5-main-video`, the same element and pattern "Play key moments" uses.
   - **What the user sees:**
     - an `aria-live` announcement ("Muting N spots…" / "Muting off");
     - the on-player pill "🔇 Muting N spots · Stop", shown while on, with "Muting now" while a span is active, styled like the key-moments pill and stacked so the two don't overlap;
     - when the transcript can't be read, a message naming a next step (open the video's transcript, or try another video).
   - **Teardown:** turning it off, in the panel or on the pill, or the page's video id changing (checked on each tick) restores `muted` only if the feature set it, and removes the listener and the pill. Closing the panel doesn't tear it down.
   - **Living with "Play key moments":** both features listen to `timeupdate`. Skip mode only seeks and the mute only sets `muted`, so they don't conflict. The plan review checks this.
3. **The word list:**
   - A new `chrome.storage.local` key, `muteWords` (a comma-separated string), edited in a new Options field.
   - A built-in default list in code, used when the key has never been set. An empty saved list means "off": the toggle says "no words listed — add some in Options".
   - The defaults are kept in step in **all three places** defaults live: `options.js` `DEFAULTS`, `background.js` `DEFAULTS`, and content.js's read (`contracts.md`).
4. **Tests (the node `vm` harness):**
   - A new `tests/js/mute_checks.js` extracts the three pure functions by their markers. It tests whole-word matching, `[ __ ]`, regex escaping, span building (lead-in, the last-cue cap, merging, an empty list), the user-mute rule, and the video-id-change teardown decision.
   - It runs from a new pytest test in `tests/test_extension_render.py`.
   - `MIN_TESTS` and its fixtures are raised.
   - `tests/test_docs_contracts.py` forces the docs update: its storage-key extractor fails until `muteWords` is listed in `contracts.md`.
5. **Docs (the `/docs` gate, in this PR):**
   - `contracts.md`: the new storage key, the new user-visible messages (they're interface copy), the panel control and the pill in the keyboard and accessibility baseline, and the new in-memory state.
   - `ux.md`: a new journey.
   - `glossary.md`: "listed words", "mute span".
