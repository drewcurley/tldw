# T-002 — Adopt the workspace model (multi-repo projects only)

## Description
For a project split across multiple repos, this forked starter is the **shared playbook**. This task wires it to the project's repos so AI agents can work across all of them safely. Skip this task entirely if the project is a single repo — the starter works repo-local out of the box (see `AGENTS.md` § 0, § 6.5).

## Acceptance criteria
- [ ] `workspace.manifest.md` filled in: every repo in the project listed with dir, role, git URL, default branch, and `contracts.md` path. No `[insert … here]` placeholders.
- [ ] All project repos checked out as **siblings** of `playbook/` under one workspace root.
- [ ] `sh scripts/setup-workspace.sh` run successfully; hooks installed (`core.hooksPath`) in the playbook and **every** repo; the script reports no unexpectedly-missing repos.
- [ ] Each code repo runs the CI mirror (GitHub Actions by default, or Azure DevOps `azure-pipelines.yml`; `ADOPTING.md` § 4), with its checks required on `main`, so `--no-verify` can't bypass gates server-side.
- [ ] `docs/integration-map.md` populated with the verified cross-repo seams (APIs, events, shared env/config, shared stores, shared packages, cross-cutting invariants). Held to the Grounding & Completeness Protocol (`AGENTS.md` § 6.0) — exhaustive and grounded, no invented edges.
- [ ] Each repo has run (or has a scheduled task to run) its own docs bootstrap (`T-001` in that repo) so each has its own `contracts.md`.
- [ ] Upstream remote configured on the playbook fork (`git remote add upstream …`) per `AGENTS.md` § 7 so the team keeps receiving starter improvements.
- [ ] This change reviewed through the full cycle (it's a major, project-shaping decision) and an ADR recorded in the playbook's `docs/decisions/` capturing the workspace-model choice and its per-repo-enforcement trade-offs.

## Risks / dependencies
- Hooks are per-repo: re-run `setup-workspace.sh` on every fresh machine / new clone. A repo without hooks installed is an enforcement hole.
- Cross-repo changes are two coordinated pull requests, not one atomic commit. Sequence producer-before-consumer (`AGENTS.md` § 7).
- **`integration-map.md` staleness is the #1 adoption risk** — a missing edge means a missed blast-radius warning, and no tooling can detect it across separate repos. Assign a named owner (in `ownership.md`) to reconcile it, use per-edge "last verified" dates, and keep it under the `/docs/*` consensus gate.
- Validate the integration-map template against this real workspace before relying on it org-wide; trim any field that doesn't earn its keep (per the 7-lens review on starter T-003).
